## B. Real registries: `sentinel scan examples/acme-demo-fixture --registry`

13 unique packages, 5 consecutive runs from this sandbox (includes Python start-up). Wall time min / median / max: **0.61 s / 0.69 s / 0.93 s**; exit codes: [0].

This is one small project from one network location at one time; it says nothing about large projects or other networks.

## What can and cannot be concluded

- The proposal's target of **under 5 seconds** is met at the default concurrency (10) for every size measured (up to 200 packages at 50 ms simulated latency). It is **not** met with concurrency 1 from 100 packages upward, which shows the speed comes from the concurrent lookups.
- The 50 ms latency is an assumption chosen for the controlled test; real registry latency varies (see section B for one observed sample).
- It is **not** proven for arbitrary projects: a project with thousands of transitive packages, a slower network, or registry rate limiting (HTTP 429 with `Retry-After`) can take longer. The retry logic is covered by tests, not by a load test.
- Cached re-runs only help within one process; there is no on-disk cache.
